# quick6-v1 可执行规则规格

> 状态：**冻结（frozen）**。本文档是 quick6 模式后续引擎与测试的规范源。
> 规则版本：`quick6-v1`；PRNG 算法版本：`quick6-prng-v1`。
> 对规则或算法版本的任何修改必须以新版本号发布，不得就地改写本文档。
> 配套可执行参考模型位于 `tests/spec/quick6/`（**仅测试侧规格参考，不构成生产引擎**）。

## 0. 范围与边界

- 本文档覆盖 quick6-v1 的全部决策、合法目标、信息可见性、胜负时点、平票、离场、
  异常步数保护以及生产/测试随机性边界。
- 凡未列出的元素一律不存在：守卫、猎人、警长、遗言、连续平票重投、夜间发言、
  中途加入/离开、按真实时间超时自动替玩家行动等。
- 本任务不实现生产引擎；`tests/spec/quick6/model.ts` 是可执行规格参考模型，
  用于把下列决策表变成可复现的断言；生产引擎后续实现必须服从本文档。

## 1. 固定配置

| 项目 | quick6-v1 决策 |
| --- | --- |
| 座位 | 6 个稳定唯一 ID 的座位（0..5），开局后不可加入或离开 |
| 玩家 | 1 真人 + 5 AI；真人座位在开局时确定，其余 5 席由 AI 控制 |
| 身份 | 狼人 ×2、预言家 ×1、平民 ×3；发牌 = 该角色多重集的无放回洗牌 |
| 阵营 | 狼人阵营：狼人；好人阵营：预言家 + 平民 |
| 开局 | 从第 1 夜开始（`round = 1`，对外阶段 `NIGHT`）；**首夜即可发生淘汰**（无首夜保护） |
| 轮次 | 每完成一次夜间结算 + 白天结算后 `round += 1`；正常规则不设轮数上限、**不设和局** |

## 2. 对外阶段状态机（外部阶段名已泛化）

| 当前阶段 | 合法输入 | 结算 / 下一阶段 |
| --- | --- | --- |
| `NIGHT` | 每个存活狼人提交一个夜间目标；存活预言家提交一次查验 | 全部提交齐后统一结算 → `DAY_DISCUSSION` 或 `END` |
| `DAY_DISCUSSION` | 按座位顺序每个存活玩家发言一次（允许显式跳过） | 全部发言完成 → `DAY_VOTE` |
| `DAY_VOTE` | 每个存活玩家投一票给另一名存活玩家（不得自投、不得弃票） | 全部投票齐后结算 → 下一轮 `NIGHT` 或 `END` |
| `END` | 拒绝一切游戏动作 | 永久终局，公开全员身份与胜负原因 |

对外阶段名仅允许上述 4 个值。内部子步骤（狼刀收集、查验收集、并票定夺、AI 待提交等）
一律不得出现在投影、事件或任何客户端可见字段中；**禁止使用 `NIGHT_SEER`、`NIGHT_WOLF`、
pending AI 座位等内部名称**。

## 3. 夜间规则（同时提交，统一结算）

- **提交**：所有夜间动作先缓冲，提交顺序不影响结算结果；结算前任何提交互相不可见。
- **狼刀**：每个存活狼人**必须**选择一名「存活且非狼」的目标（不能选自己，不能选狼人）。
  - 单狼：其选择**直接生效**。
  - 多狼同票（目标相同）：该目标被击杀。
  - 多狼不同票：由带版本的服务端 PRNG（算法 `quick6-prng-v1`，用途域 `night-wolf-tiebreak`）
    在**并列目标集合**中确定唯一受害者；给定（种子字节、算法版本、轮次、目标集合）结果完全可重放。
- **查验**：存活预言家每夜**必须**提交一次查验；目标必须是**存活且非自己**的座位；
  **允许重复查验**同一目标（跨夜不受限制）。查验结果 = 目标是否为狼人（布尔值）。
- **结算（finishNight）**：先结算查验（**无论预言家当夜是否死亡，查验结果都照常产生并保留**），
  再确定并应用狼刀受害者（只要存在存活狼人，每夜恰好淘汰 1 人）；
  公开受害者座位 ID，**不公开身份**；随后立即检查胜负（见 §5）。
- 夜间两次淘汰不可能同时发生；受害者确定与查验结算互不依赖。

## 4. 白天规则

- **发言**：存活玩家按座位顺序各发言一次；允许**显式跳过**（跳过也算完成该次发言）。
  发言即时公开；**后发言的 AI 只能看到此前已公开的前序发言**（加上公开信息与自身私有信息），
  不得提前获知后续座位的发言内容或任何私有信息。
- **投票**：随后每个存活玩家**必须**投票给另一名存活玩家；**不得自投、不得弃票**。
  - 唯一最高票：该目标被放逐。
  - 并列最高票：**无人离场**；不重投、不加赛、不使用 RNG。
- **结算（finishVote）**：应用放逐（0 或 1 人）并公开座位 ID，不公开身份；随后立即检查胜负。

## 5. 胜负判定（每次夜间淘汰与每次白天淘汰后检查）

每次夜间击杀应用后、每次白天放逐应用后，按下列顺序判定，首个命中项获胜：

| 优先级 | 条件 | 结果 |
| --- | --- | --- |
| 1 | 存活狼人数 = 0 | 好人胜 `TOWN_WIN`（reason=`WOLVES_EXTERMINATED`） |
| 2 | 存活狼人数 ≥ 其他存活人数 | 狼人胜 `WOLF_WIN`（reason=`WOLVES_MAJORITY`） |
| 3 | 其他 | 游戏继续 |

- 「其他存活人数」= 存活玩家中非狼人的数量（预言家 + 平民）。
- **正常规则不设和局**：不存在平局结局类型。只要存在存活狼人，每夜恰好淘汰 1 人，
  玩家总数单调递减，游戏必然以其中一方获胜告终。
- 离场时不揭示身份；**游戏结束后全揭示**：公开全员身份与胜负原因。

## 6. 异常防护（阶段步数上限）

- 每次成功状态迁移使 `steps` 加一；`steps` 达到上限（默认 `DEFAULT_MAX_PHASE_STEPS = 200`，
  规格模型可在构造时注入更小值用于测试）时，下一次迁移立即抛出
  `SpecAbortError(TOO_MANY_STEPS)` 中止。
- 这是**规格/实现缺陷信号**：测试必须以失败告终，**禁止把异常伪造为和局**
  （规格中不存在和局结局类型，可执行模型结构上保证这一点）。
- 非法输入（见 §8）被拒绝时状态完全不变、不计步。

## 7. 信息可见性

| 信息 | 本人 | 狼人队友 | 其他存活玩家 | 死亡玩家 / 旁观 |
| --- | --- | --- | --- | --- |
| 自己身份 | 可见 | — | 不可见 | 仅自己身份（既有私知）可见 |
| 狼人队友身份 | — | 开局起可见 | 不可见 | 不可见 |
| 预言家查验历史（目标 + 是否狼人） | 仅存活预言家可见 | 不可见 | 不可见 | 不可见 |
| 夜间各自提交的目标 | 提交者自己可见；狼人互相不可见 | 不可见 | 不可见 | 不可见 |
| 发言、白天票、对外阶段、轮数、存活状态、离场座位 ID | 公开 | 公开 | 公开 | 公开 |
| 离场者身份 | 游戏中不公开 | 同左 | 同左 | 同左 |
| 全员身份与胜负原因 | `END` 后公开 | 同左 | 同左 | 同左 |

- 服务端完整状态（含发牌种子、夜间缓冲、查验记录）不得直接发送客户端；
  必须按观察者投影（`viewFor(seat)`）后再序列化。
- **死亡玩家只能接收公开信息并观战**：系统不再向其下发任何私有信息。
- AI Provider 只接收该 AI 座位按上表可见的信息（即 `viewFor(seat)`），
  禁止把隐藏身份、其他玩家的私有数据或发牌种子放入提示词。

## 8. 非法输入决策表（一律拒绝，状态完全不变，不计步）

| 条件 | 处理 |
| --- | --- |
| 行动者已死亡 / 重复行动 / 目标已死亡 / 目标是自己 / 目标 ID 不存在 / 阶段错误 | 拒绝 |
| 狼人选狼人 | 拒绝（目标必须是存活非狼） |
| 预言家选自己 / 选已死亡目标 / 非预言家提交查验 | 拒绝 |
| 发言未按座位顺序（未轮到）/ 重复发言 | 拒绝 |
| 投票自投 / 弃票 / 重复投票 / 投票目标已死 | 拒绝 |
| 必交动作未交齐就请求结算 | 拒绝 |
| `END` 后任何游戏动作 | 拒绝 |

## 9. 随机性边界（生产 vs 测试）

- **生产发牌**：服务端生成密码学随机种子（32 字节，`crypto.randomBytes(32)`），
  经稳定算法版本 `quick6-prng-v1` + 用途域分离（`deal` 发牌、`night-wolf-tiebreak` 并票定夺）
  派生确定性流；算法版本是种子派生输入的组成部分，版本变更即产生不同流，必须随新版本发布。
- **种子保密**：种子不得进入任何投影、事件、普通日志或客户端负载；只存在于服务端受控状态中。
- **可重放性**：给定（种子字节、算法版本、用途域、调用序号）的流完全确定；
  狼刀并票结果可由（种子、算法版本、轮次、并列目标集合）复现。
- **测试**：使用至少 1000 个不同且可复现的 seed（见
  `tests/spec/quick6/randomness-boundary.test.ts`）；固定 seed fixture 与显式
  fast-check seed 保证失败可重放。

## 10. 注入约定与测试契约

- 随机性、时间、AI 输出分别经 `Rng`、`Clock`、`AiProvider` 端口注入
  （`tests/support/ports.ts`）；业务/规格代码不得直接调用 `Math.random()`、
  `Date.now()` 或真实模型 SDK。
- 默认 Vitest 环境为 Node；DOM 测试通过文件级 `// @vitest-environment jsdom` 显式选择。
- 测试 setup（`tests/setup.ts`）删除 `DATABASE_URL` 与 `DEEPSEEK_API_KEY` 并阻断全局 `fetch`：
  **默认测试不访问开发数据库，也不调用真实 DeepSeek**。
- 未来需要数据库的集成测试只能显式使用 `docker-compose.test.yml`
  （独立 project、独立库名与凭据、tmpfs 存储、无宿主端口，profile=`integration`），
  不得加载开发 `.env`。
- 验收命令：`npm run verify:test-foundation` = vitest 全量测试 + `npm run typecheck`，
  在无数据库、无浏览器、无 API Key 的环境中退出 0。
